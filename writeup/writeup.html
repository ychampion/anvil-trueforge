2Starting point

From scratch. No upstream editor project was forked, so there is no fork commit to declare and no inherited agent loop to replace. Third-party code is limited to ordinary dependencies (the TrueForge SDK, the MCP TypeScript SDK, jsdiff, zod, esbuild), credited in the README. We chose this because the editor surface we needed is small: VS Code's built-in diff editor, CodeLens and webview cover the UI, so the time went into context selection and edit safety.

3Architecture on TrueForge

VS Code extension (Anvil) TrueForge 0.185.1, local mode (127.0.0.1:8790, SQLite) ├ Agent panel / inline edit ── SDK: sessions.create, createTurnStream ──▶ agent loop: anvil-coder | anvil-inline │ ◀── SSE turn events: model.message.delta, tool.approval_required, thread.created, turn.done ──┤ │ ── user.tool_approval (allow / deny + reason) via subscribeToTurn + createTurnEvents ───────▶ │ ├ MCP server "anvil-editor" (streamable HTTP, 127.0.0.1:7391/mcp) ◀── MCP tool calls ───────────┘ │ retrieve_context · search · read_file · list_files · find_symbol · find_references │ edit_file* · create_file* · run_command* (* gated by require_approval_for_tools) └ Review engine: per-hunk accept/reject, apply via WorkspaceEdit, checkpoints, undo ── model: custom provider → vLLM on Modal
  • The extension is only a client. It never calls a model. Every turn is a TrueForge session/turn; the model is a TrueForge custom provider. The agent definitions are in trueforge/agents/*.json and are registered by trueforge/setup.mjs through TrueForge's settings API.
  • Editor capabilities are MCP tools, so the agent decides what to read and change. The extension hosts the MCP server in-process, so reads see unsaved buffers, and writes go through the editor rather than straight to disk.
  • TrueForge tool approval drives the diff review. edit_file/create_file/run_command are listed in require_approval_for_tools, so the turn pauses on tool.approval_required. Anvil reads the call's arguments from the event index, renders the proposed change hunk by hunk, and records the user's per-hunk decision keyed by (path, sha256 of the proposal). It then answers allow (≥1 hunk kept) or deny ("user rejected all hunks"). When TrueForge runs the tool, the MCP handler applies only the accepted hunks, and its result tells the model exactly what landed. An edit_file whose old_string isn't found exactly once is auto-denied with the reason, so the agent can't "confidently edit a symbol that does not exist".
  • Harness features used. Deferred tool loading: only retrieve_context, search, read_file, edit_file are preloaded, and the rest are discovered on demand. Subagents: broad exploration is delegated to a subagent that returns only paths and reasons, which keeps the main context clean. Compaction: an explicit input-token trigger (40k) sized to the model's context. Which of these shows in the Task B session: CONFIRM.

4How context is selected

Flask 3.1.3 is about 17.9k lines, far more than fits in a prompt. So Anvil never concatenates whole files: it hands the model a budgeted, ranked, explained pack, and lets the agent pull more through tools.

  • Structural index (0.2–0.3 s). Python is chunked by def/class (indentation-aware, decorators and docstrings kept, methods of big classes split out), rst/md by section, everything else in 60-line windows. A symbol table and a Python import graph are built alongside. On Flask that is 226 files, 1,493 chunks and 947 symbols.
  • Pinned first. The editor selection (expanded to its enclosing function) and explicit @file / @symbol mentions, which autocomplete in the panel, always enter the pack first.
  • Lexical retrieval. BM25 over chunks with code-aware tokens: snake/camel splitting, whole identifiers kept, light stemming, and low-weight code synonyms (cli→click/command, print→echo). It adds boosts for path and symbol-name hits, plus a "wiring" boost for a chunk that references several top hits. This is how it finds FlaskGroup.__init__, where the built-in commands are registered. Docs and tests are down-weighted at this stage…
  • …then added back structurally. Around the best source file it adds the test sibling, the docs page (by filename, module or symbol mentions, or env vars like FLASK_DEBUG), callers of the selected symbol and import neighbours. Each comes with its own reason.
  • Budget. Tokens are estimated as ⌈chars/4⌉ of the rendered snippet. Packing is greedy in priority order, with a cap per item (a hit ≤ ~25 % of the budget, a test sibling ≤ 18 %, docs ≤ 15 %). A chunk that doesn't fit degrades to an outline (signature, first docstring line, "read_file Lx–Ly for the body") before it is dropped. Every drop is recorded with its reason ("over budget: 559 tok (96 left)", "score below cutoff"). Budgets: agent pre-turn pack 6,000 tok, the retrieve_context tool 4,000 by default, inline edit 2,000.
  • Visible "why". The panel's Context chosen card lists each file, its line range, tokens used against the budget, the reason (what it defines, BM25 score and matching terms, sibling type) and what was left out. The agent's instructions require it to state which files it chose and why before editing, and retrieve_context, search and find_symbol let it widen the search itself.
  • Measured on the fixed tasks. Task B with no files named: cli.py (FlaskGroup wiring, run_command), tests/test_cli.py and docs/cli.rst, at 5,968 / 6,000 tokens, in 54 ms. Task A: get_debug_flag, its test in test_helpers.py, docs/config.rst and its callers, in 18 ms.

8Known limitations and another month

  • Retrieval is lexical (BM25 + structure). Next: a local embedding index and LSP-backed symbol graphs (references, call hierarchy) instead of regex parsing, which is Python-centric today.
  • Fallback lives in the client, because TrueForge has no per-turn model routing yet; it would be a natural harness PR.
  • Edits are applied as they're approved so the agent can run tests. Cancel restores the run checkpoint, but a crash of VS Code mid-run relies on git to recover.
